Builder detail

What actually makes it hang together

  • Single source of truth. A canonical numi-core.md file in my Drive holds the credentials, positioning and facts. Everything downstream reads from it, so the numbers never drift.
  • CLAUDE.md routing. A project instruction file acts as the routing table. It tells Claude which context to load and which skill owns which job.
  • Memory files. A memory index plus individual fact files persist across sessions: my biography, the team roster, the no em dash rule, project state and the canonical root decision.
  • Confidentiality by default. Candidate and client data is anonymised in working drafts. Real names never sit in file names. Sensitive data is flagged before it touches an external tool.
  • Human in the loop. Nothing is sent, posted or logged without my explicit confirmation. The assistant drafts and checks, I approve.

Builder detail

The eval loop is the secret

Two of the ten are quality gates, not producers. Every piece of written or search output runs through an eval skill before it reaches me, scored against the voice and the numi standard. This is a reinforcement loop: when I give feedback, the rule gets written back into memory so the next draft is better. That is what keeps quality flat as volume grows.

The numi Personal Operating System

The whole thing is held together by a personal operating system, inspired by Dave Wascha's framework and rebuilt around how numi actually works. This is the layer that turns a set of tools into a system.

Purpose

One place that defines who we are, how we work, and the rules the assistant follows. It removes the need to re-explain numi every session.

Structure

A canonical root in my Drive, a routing file, context files per domain, memory, and confidentiality rules. Locked source of truth, synced copy for the team.

The loop

Apply confirmed rules, produce work, take feedback, write the learning back into memory. Every session leaves the system a little sharper.

The learning loop

This is what keeps quality rising rather than drifting. Feedback does not evaporate at the end of a chat, it becomes a rule.

Builder detail
  • Canonical root, locked. My private Drive folder is the single source of truth and I am sole owner. The team works from a synced shared copy, so there is one master and no forks.
  • Weekly drift check. A librarian sweep checks the credentials and facts across files against the canonical core, so numbers stay consistent everywhere.
  • Ghostwriter and Reviewer. The content producer and its reviewer are separate roles. The producer drafts, the reviewer scores, and the RLHF process turns my corrections into standing rules.
  • Hard rules, every session. No em dashes. Lead with a TL;DR. Never send or delete without my confirmation. Direct and concise, answer first. These hold regardless of the task.
